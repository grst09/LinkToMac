# Roadmap

1. **Foundations** — pairing, encrypted session channel, LAN discovery. ✅ done
2. **Notifications** — `NotificationListenerService` → native banners, dismiss-sync both directions. ✅ done
3. **Calls + Messages** — call log list, SMS thread view, reply-from-Mac. ✅ done
4. **Photos** — thumbnail grid, on-demand full-res fetch. ✅ done (Photos.app import not built — out of scope for now)
5. **Screen mirroring** — `MediaProjection` capture → H.264 encode → stream → `VideoToolbox` decode/render, plus input relay via `AccessibilityService`. ✅ done
6. **Shared clipboard** — text-only sync between Mac and phone clipboards. ✅ done
7. **Files** — browse/upload/download/rename/move/copy/delete on the phone's shared storage. ✅ done
8. **Contacts** — full contact list (search, starred, colored initials avatars) with call/message actions and edit/create/delete, plus a Call History tab folded into the same section. ✅ done
9. **Polish** — proper signed `.app` bundle + notarization, connection resilience, battery-optimization onboarding, settings, notification actions, UI pass. *(next)*
10. **Desktop rewrite (Tauri)** — replacing the macOS-only `mac-app/` (Swift/SwiftUI) with a cross-platform `desktop-app/` (Rust + React) so the companion app also runs on Linux. Android side and wire protocol unchanged throughout. Phase A (handshake/crypto/identity-migration parity, proven against real hardware) ✅ done; Phase B (core shell — sidebar nav, device status card, pairing/paired-devices UI, Tailwind/Framer Motion/Lucide design system established) ✅ done. Phases C–F (feature sections, screen mirroring, packaging) not started. See the full architecture plan and phase breakdown referenced in the "Notes from building the Tauri rewrite" section below.

## Notes from building Phase 2

- **OEM `ContentProvider` quirks are real.** Samsung's call log/SMS providers reject `LIMIT n` appended to the SQL sort-order string (`IllegalArgumentException: Invalid token LIMIT`) even though that works against stock AOSP. Cap result counts in Kotlin after the query instead of in SQL.
- **`ContentResolver.registerContentObserver` throws `SecurityException` if the permission isn't granted** — unlike `query()`, which just returns null. Both call sites need the same defensive handling, or a missing permission crashes the whole service on `onCreate()`.
- **Retrofitted later: per-app notification icons.** The original `notification.posted` payload had no icon at all — the Mac row just showed the app name as text. Added `iconBase64` (`PackageManager.getApplicationIcon`, drawn to a 96×96 bitmap, PNG-encoded) to the payload, cached per `packageName` on the Android side so repeat notifications from the same app don't redraw/re-encode. The Mac falls back to the same colored-initial avatar style `InitialsAvatarView` uses for Contacts/Messages when a package's icon fails to load (e.g. system packages like `com.android.shell` don't have a normal launcher icon — Android logs a harmless internal stack trace and returns a fallback icon in that case, not an actual failure).

## Notes from building Phase 3

- The main app window (opened by clicking "LinkToMac" in the menu bar popover) now has Phone Link-style sidebar navigation: a device status card (name, connection state, battery) pinned at top, a scrollable nav list, and Settings pinned at bottom. Files and Contacts are in the nav as honest placeholders — not on the roadmap, added to match a reference design the user shared, no backend planned yet.
- Photos use paginated request/response rather than the full-snapshot model calls/SMS use — a library can hold thousands of items, so resending everything on every change doesn't scale. The Mac drives paging explicitly; full-resolution images are fetched one at a time, on demand.
- First cut shipped without any way to detect photo library changes, so deleting a photo on the phone left a stale thumbnail on the Mac with no path to correct itself. Fixed by having Android observe `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` (debounced, same ContentObserver pattern as calls/SMS) and push a `photo.libraryChanged` ping; the Mac responds with a hard reset — clear what's loaded, re-page from 0. Loses scroll position on every change, but avoids diffing thumbnail ids against a potentially huge library. Worth revisiting if this ever needs to feel less jarring.

## Notes from building Phase 4 (screen mirroring gesture input)

- **The tap/swipe pipeline shipped with `e9db385` "under debug" — the actual bug was a one-line device state, not code.** `InputInjectionAccessibilityService` was never enabled via Settings on the test device (only a third-party accessibility service was in `enabled_accessibility_services`), so `InputInjectionAccessibilityService.instance` was `null` and every `performTap`/`performSwipe` call silently no-op'd through the safe-call operator — no crash, no log, no user-visible error. `SyncForegroundService.onMirrorTapRequested` already logged the `instance` value, so `adb shell settings get secure enabled_accessibility_services` plus that log line found it in minutes once someone actually looked.
- **Confirmed with a deterministic test, not just eyeballing the mirrored home screen.** Tapping app icons on the Samsung home screen produced ambiguous results (taps "completed" per the `GestureDescription` callback, but no app visibly launched) — plausible near-misses on small OEM dock icons, not conclusive either way. Opened the Calculator app instead (`adb shell am start -n com.sec.android.app.popupcalculator/.Calculator`) and had a real click land on "5": the digit appeared in the display, `adb exec-out screencap` before/after made it unambiguous. Large-target, high-contrast apps make far better manual test fixtures than a home screen full of small icons.
- **`resources.displayMetrics` inside the accessibility service already excludes system-bar insets** (~153px on this device), and the `MediaProjection` virtual display was originally sized to that same "usable" aspect ratio, not the full physical panel — so `toScreenPoint()`'s normalized→pixel math lines up correctly without any extra letterbox correction, regardless of what the virtual display's actual pixel dimensions are (aspect ratio is what matters, not resolution). Looked like a plausible second bug during triage; turned out to be intentional and consistent, and stayed consistent after later raising the resolution — see below.
- **`print()` statements without `fflush(stdout)` are invisible when the binary's output is redirected to a file** (block-buffered instead of line-buffered off a tty) — this bit the Mac-side tap/swipe logging in `ScreenMirrorView.swift` the same way it bit clipboard logging earlier. Added `fflush(stdout)` after every print in the mouse-event path to match the convention already used in `ConnectionServer.swift`.
- **Multi-display foldables complicate `adb screencap`/`wm size`.** This device (Z Fold) reports multiple `DisplayInfo` entries (cover screen off, main screen on, plus virtual displays for Studio's screen-sharing and LinkToMac's own mirror capture); `adb shell screencap -d <id>` needs the physical display address from `dumpsys SurfaceFlinger --display-id` (a `local:<StablePhysical id>` string), not the logical `mDisplayId` from `dumpsys display` — passing the wrong one either grabs the wrong display or fails outright.

### Follow-up: mirror resolution/bitrate, and a real crash hiding behind the gesture bug

- **The video was genuinely low-res, not just perceived that way.** `H264Utils.scaledDimensions` capped the long edge at 1280px (vs. the phone's native ~2367px usable height) and the encoder ran at a flat 4 Mbps — both simple constants, not derived from anything device-specific. Since this streams over LAN, bandwidth is not the constraint; raised the cap to remove downscaling entirely (mirrors at native "usable" resolution now) and bitrate to 16 Mbps with `KEY_BITRATE_MODE` set explicitly to VBR. Because `scaledDimensions` always preserves the source aspect ratio, this didn't require touching any of the tap/swipe coordinate math above.
- **A real, pre-existing crash was found while testing this, unrelated to resolution/bitrate.** `ScreenMirrorService.stop()` called `context.startForegroundService()` unconditionally. The manifest declares this service's `foregroundServiceType="mediaProjection"`, and Android 14 requires an *active* capture grant to satisfy `startForeground()` for that type — so if the service process had already died (observed here after switching apps during testing, likely OEM memory pressure), a "Stop Mirroring" click tried to resurrect it just to tell it to stop, had no grant to satisfy the type check, and crash-looped (`ActivityManager: Rescheduling restart of crashed service ... for mem-pressure-event`, repeating). That churn is also why the accessibility service showed `instance=null` afterward — the whole app process was restarting. Fixed by switching `stop()` to `context.stopService()`, which is a no-op if nothing is running and doesn't carry the foreground-type obligation; `onDestroy()` already calls `stopCapture("requested")` for the case where something *is* running.
- **Home-screen swipes/taps still looked unreliable even after both fixes above**, while the dedicated back/home/recents buttons (a different code path — `performGlobalAction`, not `dispatchGesture`) kept working. Not yet root-caused; suspect Samsung's One UI launcher filters synthetic touches for icon/page navigation specifically, since the same gesture dispatch mechanism was already proven to work cleanly against a non-launcher app (the Calculator test above). Worth retesting against a plain scrollable app (e.g. Settings) rather than the launcher before concluding anything further.

## Notes from building the Tauri rewrite (Phase A)

- **The one thing that could have silently broken every already-paired phone: identity key continuity.** Android pins the Mac's P-256 public key after first pairing and rejects any reconnect where it's changed (a deliberate MITM check — see docs/PROTOCOL.md's handshake section). The old Swift app's identity key was never in Keychain — just plain JSON at `~/Library/Application Support/LinkToMac/identity.json` (`{deviceId, rawPrivateKey}`, base64 raw 32-byte P-256 scalar). `desktop-app/src-tauri/src/store/identity.rs` checks that exact path on first launch and imports the raw key bytes verbatim before ever generating a new one — confirmed working via log output (`migrated identity from old Swift app at ...`) and, separately, a live reconnect test (see below) proving the mechanism itself is sound.
- **The actual end-to-end proof required a fresh pair, not a migrated one** — mid-session, the Android app's own data got wiped (uninstalled at some point outside this session, unrelated to the rewrite), which erased Android's stored pin/device-token and made the "reuse the *old* Swift-established pairing" scenario untestable as originally planned. Pragmatic fallback: built just enough pairing UI (QR generation + display, a `begin_pairing` Tauri command) to do a fresh pair against the *new* Rust server, then force-reconnected (`adb shell am force-stop` + relaunch) and confirmed the log showed `reconnect — no re-pair required`, not `new pairing`. This proves the reconnect mechanism itself works correctly — pin validation, device-token lookup, salt-based session re-derivation — even though it couldn't prove continuity with the specific pairing the old Swift app had established. Worth remembering: a "prove X survives a migration" test needs the pre-migration state to actually still exist: verify that first, next time.
- **Rust crypto crate APIs were more in-flux than expected.** `p256` 0.14 / `aes-gcm` 0.11 / `aead` 0.6 all deprecated their old rng-taking APIs (`SecretKey::random(&mut rng)`, `Nonce::from_slice`, `Aes256Gcm::generate_nonce`) in favor of a shared `Generate` trait (`SecretKey::generate()`, `Nonce::generate()`, both re-exported identically from both `aead` and `elliptic-curve` — importing either satisfies the other, which is why one of the two imports triggered an "unused import" warning). Getting `Generate::generate()`'s no-arg convenience method requires explicitly enabling each crate's `getrandom` feature (and `aes-gcm`'s separate `rand_core` feature) — none of this is obvious from the compiler errors alone, which just say "method not found," not "enable this feature." Worth checking a crate's own doc-comment usage examples (`grep` the crate's `src/lib.rs` under `~/.cargo/registry/src/`) before guessing at API shape from memory, especially for fast-moving crates like the RustCrypto ecosystem.
- **`if-addrs` (already a transitive dependency of `mdns-sd`) was enough for the LAN-IP lookup** the pairing QR needs (`host` field) — no need for a separate IP-address crate; same POSIX-`getifaddrs`-equivalent job `LocalNetwork.swift` did, just via an existing dependency instead of raw FFI.
- **Avoid the `image` crate for anything as simple as "render a QR code."** Initially added `image` + `qrcode` (Rust crates) to generate a QR PNG server-side, which pulled in a huge, mostly-irrelevant dependency tree (AV1 encoders, TIFF support, `rayon`, etc.) for what's a trivial job. Removed both — the frontend renders the QR client-side from the plain JSON payload via the `qrcode` **npm** package instead, which was the original plan all along and needed zero extra Rust dependencies.
- **`ServiceDaemon` (mdns-sd) must be kept alive for the advertisement to persist** — it's a real background-thread-owning object, not a fire-and-forget registration call. Stored in `AppState` (leading underscore field, `_mdns`, since nothing reads it directly — it just needs to not be dropped) rather than the tempting-but-wrong `std::mem::forget`, which would leak it uncontrolled instead of tying its lifetime to the app.
- **`adb`'s USB connection to the test device dropped twice mid-session** (once genuinely unplugged, once just an `adb` daemon hiccup fixed by `adb kill-server && adb start-server`) — worth checking `adb devices` before assuming a "phone not responding" symptom is an app bug.

## Notes from building the Tauri rewrite (Phase B)

- **Tailwind's JIT scanner needs literal class strings, not runtime-interpolated ones.** First pass at per-section accent colors used a `` `text-${hue}-500` `` template-literal helper — Tailwind's build-time content scanner can't evaluate that, so every one of those classes would've silently been missing from the compiled CSS (no error, just no color). Fixed by spelling out each color's full class set as a literal object (`src/theme/sections.ts`'s `ACCENTS` map) instead of generating strings at runtime. Worth remembering for any future per-item dynamic styling — if a Tailwind class name isn't a complete string literal somewhere in the source, assume it won't ship.
- **The old app split pairing UI across two surfaces** — `DeviceStatusView.swift` (connection status, in the main window) and `MenuBarView.swift` (QR pairing flow + paired-devices list, in the menu-bar popover). This app doesn't have a tray/menu-bar surface yet (that's packaging work, later-phase), so `ThisDeviceView.tsx` deliberately merges both into one section rather than leaving pairing with nowhere to live until Phase F.
- **The disconnect/reconnect toggle from `SidebarDeviceCard.swift` wasn't ported** — the Rust WebSocket server currently binds once at startup and runs forever (see `net/server.rs`'s `run()`); there's no `stop()`/`start()` pair to wire a toggle to yet. Deliberately left out rather than shipping a switch that doesn't do anything. Worth a small follow-up when needed: `AppState` would need to hold the `TcpListener`/mDNS registration behind something restartable rather than owning them for the process lifetime.
- **`forget_device` doesn't sever an already-active connection to that device** — it removes the stored credentials (so *reconnecting* will require a fresh QR pair), but if that phone happens to be the one currently connected, the live WebSocket keeps running until it disconnects on its own. The old Swift app's `forgetDevice` explicitly called `disconnect()` first because it held a direct reference to the active connection; this app's `AppState` doesn't thread a handle to the live connection through to command handlers yet. Fine for the common case (forgetting a device you're not actively using), worth revisiting alongside the disconnect-toggle work above since they need the same plumbing.
- **Verified the rendered UI via the Browser pane pointed at the Vite dev server (`http://localhost:1420`)** rather than screenshotting the real desktop — same rendered output as the actual Tauri window (confirmed both picked up the same HMR updates from the dev log), without the risk of capturing unrelated content on-screen. `invoke()` calls fail there with "Cannot read properties of undefined" since the Tauri IPC bridge only exists inside the real webview — expected, not a bug, and a useful way to tell the two apart when reading error output.

## Notes from building Files + Contacts (Phases 6–7)

- **`Organization` has no dedicated `CONTENT_URI`** (unlike `Phone`/`Email`, which do) — it's a row in the generic `ContactsContract.Data` table, filtered by mimetype. Querying it the same way as phone/email throws instead of just returning empty.
- **A permission-gating bug nearly made `WRITE_CONTACTS` unrequestable.** `isCallsAndMessagesAccessGranted()` only checked `READ_CALL_LOG`/`READ_SMS`/`SEND_SMS` — all already granted from an earlier phase — so the "Grant Access" card that triggers the permission request never reappeared once `WRITE_CONTACTS` was added to the manifest. A user who'd already granted everything else had no UI path to ever be prompted for the new permission. Fixed by including `WRITE_CONTACTS` in that same gating check, same reasoning as why `READ_CONTACTS` is deliberately excluded from it (see the comment there) — but here the permission is load-bearing for a real feature (contact edit/create/delete), not just a nice-to-have.
- **SMS send/delete for third-party apps is close to a dead end** — see docs/PROTOCOL.md's "Not implemented" section. Short version: Android restricts all writes to `content://sms` (insert *and* delete) to whichever app holds the default-SMS-app role, which LinkToMac deliberately doesn't take on. Sending to a brand-new number still transmits but never gets recorded for the Mac to see again (worked around client-side with a local-only echo thread); deleting any thread was attempted and reliably rejected on real hardware, so that feature was pulled entirely rather than shipped broken. RCS conversations are invisible to any third-party reader, full stop — no workaround exists.
- **Android's SMS delete restriction was confirmed by directly querying the provider**, not inferred — `adb shell content query --uri content://sms --where "address='...'"` showed zero rows for a message the phone's own default SMS app displayed as sent. Worth remembering as a debugging technique: when Android behavior seems to contradict what a first-party app shows, query the underlying `ContentProvider` directly rather than trusting the first-party app's UI as ground truth.

## Tech stack

| Layer | Mac | Android |
|---|---|---|
| UI | Swift + SwiftUI | Kotlin + Jetpack Compose |
| Transport | `Network.framework` WebSocket (`NWProtocolWebSocket`) | OkHttp WebSocket |
| Discovery | Bonjour (`NWListener` service advertisement) | NSD (`NsdManager`) |
| Crypto | CryptoKit: P-256 ECDH, HKDF, AES-GCM | `java.security`/`javax.crypto`: EC ECDH, HKDF (RFC 5869 via HMAC), AES-GCM |
| Messages | `Codable` JSON | `kotlinx.serialization` JSON |
| Pairing transport | QR (CoreImage `CIQRCodeGenerator`) | ZXing (`zxing-android-embedded`) |
| Secrets storage | Keychain (planned) / JSON in Application Support (interim) | `EncryptedSharedPreferences` |
